# CODEWAVE

## Industry-Grade Offline Hi-Res Music Player for Android

**Product type:** Native Android local music player
**Primary platform:** Android phones
**Secondary targets:** Android Auto, Wear OS, tablets/large screens
**Connectivity:** Offline-first; internet optional and only required for updates
**Account:** None
**Cloud library:** None
**Streaming:** None
**Ads:** None
**Analytics:** None by default
**Primary differentiator:** VS-Code-inspired developer aesthetic combined with audiophile-grade local playback and an extremely fast local library.

---

# 1. PRODUCT VISION

CODEWAVE is a premium, completely local Android music player for people who own their music.

It must:

* discover local audio rapidly
* play music reliably in foreground/background
* expose meaningful technical audio information
* preserve lossless playback whenever the Android audio path permits it
* provide professional library organization
* provide a serious equalizer/DSP system
* remain usable without an internet connection
* feel instantaneous
* survive Android process death
* recover gracefully from media/file/device changes
* integrate properly with Android system media controls
* provide optional GitHub Release-based sideload update discovery
* maintain a polished, coherent visual system

CODEWAVE is **not**:

* a streaming service
* a downloader
* a social network
* an account-based music platform
* a cloud music locker
* a generic MP3 player with a themed skin

---

# 2. CORE PRODUCT PRINCIPLES

## P0 — Local ownership

The user's music remains on their device.

No account is required.

No cloud database is required.

No network is required for:

* scanning
* browsing
* searching
* playlists
* favorites
* playback
* EQ
* sleep timer
* queue management
* album art
* metadata editing

---

## P0 — Playback reliability beats visual complexity

The player must never sacrifice playback reliability for animations.

If the device is under memory pressure:

1. visual effects degrade
2. album-art prefetching is reduced
3. expensive visualizers disable
4. playback remains unaffected

---

## P0 — Never lie about audio quality

CODEWAVE must distinguish:

**File properties**

from

**actual playback/output properties.**

For example:

> FLAC · 24-bit · 96 kHz

means the file contains that format.

It must NOT imply that the user is necessarily receiving 24-bit/96-kHz output from the hardware.

The UI should therefore distinguish:

**SOURCE**

`FLAC · 24-bit · 96 kHz · Lossless`

and, where technically obtainable:

**OUTPUT**

`48 kHz · 24-bit · PCM`

If output information cannot be reliably determined:

`Output information unavailable`

Never fabricate it.

# 33. LOSSLESS AUDIO POLICY

CODEWAVE must preserve the source PCM data whenever the complete playback path supports it.

It must NOT perform:

* unnecessary transcoding
* lossy conversion
* hidden normalization that alters source data
* unnecessary resampling

However, Android hardware/audio routing may impose its own format conversion.

Therefore:

**“Lossless file” ≠ “bit-perfect hardware output.”**

This distinction is mandatory.

# 36. EQUALIZER / DSP

This is where most amateur music-player implementations become garbage.

Do not implement a fake EQ consisting of sliders that don't actually affect the audio path.

Use a dedicated DSP abstraction.

Architecture:

```text
Source
  ↓
Decoder
  ↓
PCM
  ↓
DSP Pipeline
  ├── Preamp
  ├── Parametric/Graphic EQ
  ├── Bass control
  ├── Loudness
  ├── Compressor
  ├── Limiter
  └── Optional spatialization
  ↓
Audio Output
```

Android provides `DynamicsProcessing`, which includes EQ, multiband compression and limiting, with realtime-controllable parameters.

Android also provides Equalizer and other AudioEffect APIs, but effects must be attached to the relevant audio session; global session-0 insertion effects are deprecated.

# 42. FAST DISCOVERY

Primary source:

**MediaStore**

Use incremental change detection.

Maintain:

```text
mediaStoreId
contentUri
dateModified
size
duration
metadataHash
fileFingerprint
```

When a new file appears:

1. detect candidate
2. validate media type
3. extract metadata
4. fingerprint
5. insert/update database
6. update indexes
7. update UI

The UI must never block waiting for a full scan.

---

# 43. DOWNLOAD-DETECTION BEHAVIOR

When a music file is downloaded:

```text
File appears
      ↓
MediaStore publishes change
      ↓
CODEWAVE receives change
      ↓
Candidate queued
      ↓
Metadata extracted
      ↓
Database updated
      ↓
Library UI updates
```

If MediaStore notification is delayed:

periodic reconciliation must eventually detect the file.

Do not rely on one notification mechanism.

# 44. PARTIALLY DOWNLOADED FILES

Critical edge case.

Example:

```text

```

Do NOT immediately treat it as a valid playable song.

```text

↓
VALIDATING
↓
READY
```

If file changes while processing:

restart validation.

# 63. DATABASE CORRUPTION

The database layer must have recovery strategy.

Potential sequence:

```text

↓
close database
↓
restore valid backup if available
↓
otherwise rebuild library index
↓
preserve user configuration where possible
↓
notify user
```

The music files themselves must never be modified by database recovery.
